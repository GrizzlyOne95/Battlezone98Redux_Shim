[h1]Roadmap[/h1]

This is a rough roadmap for where I'd like to take the Battlezone 98 Redux community patch / OpenShim / Extra Utilities work next.

[b]Last major audit: 2026-08-31.[/b]

This is [b]not a promise that features will arrive in this exact order[/b]. A lot of this work depends on reverse engineering, testing, and whether a feature can be implemented safely without introducing worse problems than it solves.

The general priority remains:

[b]Fix crashes and broken stock behavior first, then improve compatibility and multiplayer longevity, then expand the modding API and visual features.[/b]

The roadmap now separates four states that used to get mixed together:

[list]
[*] [b]Active / Open[/b] - the defect or feature is still genuinely unresolved.
[*] [b]Implemented - Qualification Pending[/b] - code exists, but live, multiplayer, visual, or lifecycle acceptance still has a meaningful open gate.
[*] [b]Completed / Restored[/b] - the work is sufficiently understood and implemented to leave the active backlog.
[*] [b]Disproven / Reclassified[/b] - reverse engineering showed that an old community report was stock behavior, the proposed root cause was wrong, or the work is an enhancement rather than a compatibility restoration.
[/list]

[h2]High Priority[/h2]

[h3]GOG Workshop Compatibility[/h3]

Steam users already automatically download Workshop content required by multiplayer games. GOG users do not have that integration, which makes joining Steam-hosted modded games considerably more awkward.

The idea is to add an [b]optional GOG Workshop bridge[/b].

When a GOG player attempts to join a game using a Steam Workshop map/mod, OpenShim could identify the required Workshop item and offer to download and stage it automatically.

The likely implementation would use a small external helper rather than performing network/download work inside Battlezone itself.

This would be explicitly opt-in so OpenShim is not unexpectedly launching helper processes in the background.

Potential flow:

[code]
Join multiplayer game
        |
Required Workshop item missing
        |
"Download required content?"
        |
Steam/community download helper
        |
Validate + stage mod for GOG
        |
Refresh content
        |
Join game
[/code]

If anonymous Steam Workshop downloads work reliably for Battlezone's Workshop, this could close one of the biggest remaining Steam/GOG multiplayer compatibility gaps.

[h3]Mod Dependency Support[/h3]

Steam Workshop supports required/dependent Workshop items, but Battlezone itself does not understand those relationships.

For example:

[code]
Mod A
 |- requires Mod B
 |- requires Mod C
[/code]

Steam may download all three, but Battlezone still effectively treats them as unrelated addons.

I'd like OpenShim to understand a real dependency graph so it can:

[list]
[*] Detect missing dependencies
[*] Detect dependencies that are installed but unavailable to the current mod
[*] Recursively resolve dependency chains
[*] Show useful dependency errors instead of mysterious missing assets
[*] Integrate dependency downloading with the GOG Workshop bridge
[*] Potentially support minimum OpenShim / EXU versions later
[/list]

This could eventually become the basis of a much cleaner mod-loading system.

[h3]Community Multiplayer / Matchmaking Preservation[/h3]

A replacement BZRNet matchmaking service is already under active development.

The current prototype includes:

[list]
[*] WebSocket lobby support
[*] Lobby creation/joining
[*] Chat and lobby metadata
[*] UDP endpoint discovery
[*] Experimental UDP relay support
[*] Server persistence
[*] Health/admin tooling
[*] Native OpenShim control-plane and datagram instrumentation
[*] Live nickname re-authorization support
[/list]

The long-term goal is to make multiplayer survive even if Rebellion's official service eventually disappears.

I'd like OpenShim to eventually expose something similar to:

[code]
MULTIPLAYER SERVICE

Official Rebellion
Community Server
Automatic Failover

[ Test Connection ]
[ Host Server ]
[/code]

[b]Automatic Failover[/b] could attempt the official service first and use the community service if it is unavailable.

I'm also interested in an integrated [b]Host Server / Host Game[/b] option.

Rather than forcing users to manually configure a separate server, hosts file, launch arguments, etc., OpenShim could launch a bundled matchmaking/server helper and automatically point the local Battlezone client at it.

For permanent community matchmaking, a dedicated public service would still be preferable, but local hosting could be extremely useful for LAN games, private groups, development/testing, and emergency multiplayer fallback.

[h3]Netcode Reliability Qualification[/h3]

The networking work is much further along than the old roadmap implied. OpenShim now owns all ten relevant live [Net] tunables instead of relying on a net.ini file Redux may never apply, and the current tuning is aligned with the final V5.3 behavior from the community netcode-patch work.

Implemented work includes:

[list]
[*] MinBandwidth / MaxBandwidth / UpCount / DownCount / MaxPing / MaxPingsLost handling
[*] Relaxed host auto-kick envelope
[*] Per-global sanity gating so moved addresses fail closed
[*] Governor cold-start versus floor-collapse classification
[*] Outbound packets/sec and bytes/sec burst telemetry
[*] Receive-side packet reordering experiments and extensive BZRNet tracing
[*] [Network] GovernorTuning = OpenShim / Stock so strict-parity lobbies can restore stock tuning without reconstructing net.ini
[/list]

The remaining work is no longer "find some better bandwidth numbers." It is controlled network qualification:

[list]
[*] Reproduce packet-loss / burst cascades under controlled impairment
[*] Verify the BZR packet header/ACK layout before adding per-peer RTT sampling
[*] Determine the real AutoKickLoss units and dead-peer behavior
[*] Decide whether packet reordering materially improves bad links without hiding a deeper failure
[*] Keep retransmit suppression and send pacing disabled unless evidence proves they are safe; V5.3 backed the retransmit damper out for good reason
[/list]

[h3]32-bit Mission Resource / Address-Space Lifecycle[/h3]

Windows Redux 2.2.301 is already [b]Large Address Aware[/b]. There is no missing PE-header switch that can give the 32-bit executable more useful address space on 64-bit Windows.

The practical x86 memory problem is therefore resource retention and/or virtual-address fragmentation, especially across large custom campaigns with high-resolution textures and high-poly meshes.

Redux already contains internal cWorkshop resource-rebuild paths that clear and reinitialize the Ogre [code]Modable[/code] resource group. The open question is whether ordinary mission-to-mission transitions inside one campaign bypass that cleanup and retain mission-specific resources.

The current plan is:

[list]
[*] Add committed/private/working-set and virtual-address telemetry
[*] Track total free VA and, critically, the largest contiguous free VA region
[*] Count Ogre textures, meshes, skeletons, materials, and Modable resources around mission transitions
[*] Use a deterministic multi-mission heavy-asset fixture to prove or disprove cumulative retention
[*] Only after retention is proven, identify the exact safe teardown window and test the least destructive resource unload first
[/list]

This is an x86 mitigation track, not a substitute for a true Win64 build.

[h3]Windows x64 Reconstruction Research[/h3]

A major new research opportunity appeared in August 2026: the shipped macOS Battlezone 98 Redux 2.2.301 executable is a real [b]x86-64 peer build[/b], not a 32-bit binary in a wrapper.

The Mac executable preserves C++ names, RTTI, vtables, function starts, unwind metadata, translation-unit names, and direct 64-bit object layouts. It also provides strong evidence that important game-facing formats are already architecture-independent: Lua/game handles remain 32-bit opaque identifiers and GameObject save/load uses typed fields with explicit byte counts instead of dumping native structs.

The immediate research target is DistributedObject / GameObject networking and serialization, with Mac-to-Windows correlation used to answer:

[list]
[*] Which engine/game systems are inherently 64-bit clean
[*] Which fields are true pointers versus intentional fixed-width handles/IDs
[*] Whether network/save formats are pointer-size independent
[*] Which Windows-only middleware or ABI assumptions would block a source-equivalent Win64 reconstruction
[*] How much of the anonymous Windows executable can be named defensibly from the symbol-rich Mac peer
[/list]

This is [b]research, not a promise to replace Redux with a new engine[/b]. It materially improves the long-term feasibility picture and should remain visible alongside the x86 lifecycle mitigation work.

[h3]Raw Mouse Input - Finish Qualification[/h3]

Redux already contains a real native Windows Raw Input path, including the stock rawinput/norawinput launch options and WM_INPUT handling.

OpenShim now exposes that native path as an explicit opt-in through [code][General] RawMouseInput = 1[/code] and the native Settings page. The shipped player preset leaves it off, so installing the DLL alone does not change mouse behavior.

The implementation also handles absolute-mode pointing devices so remote-desktop, VM/KVM, and tablet-style input does not feed absolute 0..65535 coordinates into a relative look accumulator.

Remaining qualification includes sensitivity, focus/Alt-Tab transitions, high polling-rate mice, frame-rate independence, and broad hardware/remote-input compatibility.

[h2]Extra Utilities / Modding API[/h2]

[h3]Native Event / Callback System[/h3]

EXU already exposes a huge amount of game state, but many scripts still have to constantly poll for changes.

I'd like to eventually expose native events such as:

[code]
OnDamage
OnKill
OnTargetChanged
OnPilotEnter
OnPilotExit
OnCommand
OnBuildSelection
OnWeaponFired
OnPlayerJoined
OnPlayerLeft
[/code]

The safe design is still for native hooks to queue events and deliver them to Lua during a known-safe update point rather than executing arbitrary Lua from deep inside engine functions.

[h3]Custom Unit Commands[/h3]

EXU can currently replace the selected unit's stock Hunt command with Lua-controlled behavior.

The larger goal remains:

[b]Allow Lua scripts to add/remove/replace unit command buttons directly.[/b]

For example:

[code]
SALVO
CLOAK
DEPLOY
REPAIR
FORMATION
SPECIAL
[/code]

with custom labels, availability conditions, and Lua callbacks.

[h3]Custom Producer / Build Menus[/h3]

Related to unit commands is expanding Recycler, Factory, Armory, Constructor, and generic Producer menus.

The eventual goal is nested menus such as:

[code]
FACTORY

Combat Units >
    Tank
    Bomber
    Scout

Support Units >
    Tug
    APC
    Scavenger
[/code]

Battlezone already has similar menu behavior internally for editor/build systems, so this appears feasible, but still requires significant native integration.

[h3]Higher-Level Multiplayer Lua Replication[/h3]

This is less one "multiplayer sync bug" and more a limitation of how Battlezone's multiplayer systems are divided. Object existence, distributed-object ownership, mission variables, UI/objectives, names, cameras, and weapon state do not all use one automatic replication layer.

EXU already exposes synchronized/asynchronous object creation and network identity helpers. Working co-op frameworks also prove that host-authoritative mission logic plus explicit Send/Receive-style synchronization can be reliable.

The remaining goal is a coherent high-level API for common operations such as:

[list]
[*] Spawn/remove
[*] Shared mission/state variables
[*] SetName()
[*] Objective text/markers
[*] Weapon/loadout changes
[*] Custom synchronized events
[*] Ownership-sensitive operations
[/list]

This should be built on individually understood engine behavior rather than hiding unknown ownership rules behind a generic SyncEverything() abstraction.

[h2]OpenShim Interface Improvements[/h2]

OpenShim already has its own Settings page and rewritten key-binding interface.

The renderer/profile selector is also [b]already implemented[/b]:

[list]
[*] Renderer: Auto / DirectX 9 / DirectX 11 - restart required
[*] Render Profile: Retro / Redux / Enhanced - applies live
[/list]

The shipped/default policy is deliberately conservative: Auto renderer and the Redux compatibility profile rather than assuming the newest renderer/profile is automatically best.

The remaining UI direction is organization and discoverability rather than basic renderer selection. Longer term I'd like proper submenus such as:

[code]
OPENSHIM

Gameplay
Input
Video / Renderer
Multiplayer
Mods
Diagnostics
[/code]

Recent Settings/Keybind work also moved both pages onto a shared measured layout with stock-derived framing, wrapped help text, and clickable value controls. Future UI work should preserve that common layout rather than adding more hand-positioned widgets.

[h2]Audio / Soundtrack Control[/h2]

Redux contains a native OGG soundtrack system separate from normal Lua WAV playback.

EXU currently exposes things such as music-volume settings, but it does not yet provide full control over the native soundtrack manager.

I'd like to expose functions for:

[code]
Play track
Stop
Pause
Resume
Change track
Potentially fade/change music state
[/code]

That would allow campaign mods to use proper compressed dynamic music without converting entire soundtracks to WAV files.

[h2]Environment / Terrain Runtime Control[/h2]

EXU can already manipulate a surprising amount of the live environment:

[list]
[*] Terrain materials/textures
[*] Fog
[*] Ambient lighting
[*] Sun lighting/direction
[*] Time of day
[*] Sky systems
[*] Gravity
[*] Shadows
[*] Visibility
[/list]

The renderer work is also more mature than the old roadmap text suggested:

[list]
[*] Enhanced PSSM has a BZCC-informed comparison-PCF / cascade-blending path under controlled qualification.
[*] The abrupt PSSM shadow cutoff was traced to Redux applying shadowFarDistance=128 while the cascade contract extends to roughly 256; an OpenShim far-distance override exists as a quarantined experiment.
[*] Enhanced linear-light art direction was corrected for double-encoded mission fog and an overly strong neutral terrain diffuse-IBL floor on airless/distant terrain.
[*] DX11 Enhanced can reach the 24-light shader capacity; contribution-ranked light selection exists experimentally and still needs final visual/performance acceptance.
[*] The fullscreen "sun flashbang" was isolated to a dedicated ScreenFlash call and can now be suppressed independently without disabling the sun, lens flare, shadows, or explosion flashes.
[/list]

Eventually I'd still like to wrap the existing environment controls into higher-level presets, for example:

[code]
LoadEnvironment("MarsNight")
LoadEnvironment("EuropaStorm")
LoadEnvironment("LunaDay")
[/code]

This remains below stability, multiplayer preservation, and core modding infrastructure in priority.

[h2]Active / Open Engine and Gameplay Work[/h2]

[h3]Crash / Stability Bugs[/h3]

[list]
[*] [b]Pilot hardpoint ODF ordering crash[/b] - 1.5 warns instead of crashing, so this still appears to be a Redux-specific parser/state regression. The exact Redux crash consumer needs a controlled repro/minidump.
[*] [b]weaponMask=00000 Follow crash[/b] - the encoded mask and several consumers are known, but the exact Follow-path fault still needs to be captured. The fix must preserve intentionally weaponless units rather than rewriting the mask.
[*] [b]Shift-F9 editor task-mode crash[/b] - selecting a unit whose classLabel and AI process do not match can crash the editor. This is especially relevant to legacy/custom mission units.
[*] [b]Second-session editor corruption/crash[/b] - entering the editor works normally the first time, but after returning to menu and loading another mission in the same process the minimap can be empty and changing a terrain tile reliably crashes. This remains a strong mission-lifetime/state-reset candidate.
[*] [b]DX11 / renderer lifetime instability[/b] - several distinct DX11/Ogre lifetime problems have already been found and patched. Remaining crashes, texture failures, fullscreen transitions, Alt+Tab/Alt+Enter, and shutdown failures should continue to be tracked by individual crash signatures instead of one generic "random DX11 crash."
[*] [b]Multi-parameter command-line parsing regression[/b] - Redux performs destructive command-line tokenization early in startup. The exact multi-option failure path and 1.5 parity trace still need to be pinned down before patching argument handling.
[/list]

OpenShim now has first-chance/unhandled crash logging and minidump capture, so deterministic crashes should increasingly be handled as:

[code]
reproduction
 -> crash signature / module + RVA
 -> native root cause
 -> narrowly scoped guarded patch
[/code]

[h3]Gameplay / AI Bugs and Decision Gates[/h3]

[list]
[*] [b]AIP mixed stock/custom producer bug[/b] - when custom and stock units are mixed in a custom producer, AI may only build the custom units even when stock units are present in the AIP. The stock-vs-custom selection logic still needs to be compared against legacy behavior.
[*] [b]Captured/disguised AI victim retaliation parity[/b] - capture/disguise writers, actual-team hostility, and hostile-hit state have strong 1.5/Redux static parity evidence. Do not close the historical report yet: captured craft, turrettank, static turret/gun-tower, and sniper-specific victim response still need a controlled runtime 1.5-versus-Redux matrix.
[*] [b]Neutral-unit attack/order asymmetry[/b] - neutral units can attack the player while the player cannot issue equivalent attack orders against them. Revalidate first, then compare against 1.5 team/order rules.
[*] [b]Rare sniper/reticle misalignment after eject[/b] - occasionally the pilot sniper aim no longer agrees with the reticle after ejecting. Needs a reliable reproduction before patching.
[*] [b]Walker cockpit jitter[/b] - parent-transform inheritance remains implicated, but a safe fix must preserve cockpit animation, aiming, and first-person offsets.
[/list]

[h3]Multiplayer Bugs[/h3]

[list]
[*] [b]Packet-loss / traffic-storm recovery[/b] - baseline tuning and telemetry are now substantially improved; the remaining defect is the broader loss/recovery cascade under real impairment and how Redux's resend/governor behavior interacts with it.
[*] [b]Armory / Daywrecker duplicate detonation in multiplayer[/b] - one launched Daywrecker can produce multiple effective detonations/explosions, especially for non-host clients. Likely authority/replication work, but still needs proof.
[*] [b]Daywrecker multiplayer terrain-spire corruption[/b] - multiplayer Daywrecker terrain deformation can produce the known terrain-spire artifact. Keep this separate from duplicate detonation.
[*] [b]Splinter multiplayer payload duplication[/b] - likely ownership/authority related, but the correct peer-authority gate needs to be proven before changing replication behavior.
[*] [b]Splinter deployed collision response[/b] - deployed SprayBuildingClass objects can produce violent collision/reaction behavior; the collision impulse owner has not yet been isolated.
[*] [b]Password-lobby friend invites[/b] - the invite path does not include the password, making password-protected friend invites fail. This belongs with the broader multiplayer service/client work.
[*] [b]MPI host-leaving bug[/b] - host departure behavior still needs a proper reproduction and state/ownership trace.
[*] [b]Multiplayer freecam exploit[/b] - the camera path and authoritative network-game gate still need to be joined cleanly without breaking legitimate SP/editor/spectator use.
[*] [b]All Nations multiplayer option[/b] - this is a real stock 1.5 host rule. The reconstructed contract is Net::bNations, serialized in the existing game-info blob and consumed by nation-sensitive vehicle/class/mission paths. Redux retains the variable and consumers but the shell presentation is dormant. Restoration should reuse the existing rule byte and add the missing settings-row/UI path rather than inventing a new protocol.
[/list]

[b]Important Cloak distinction:[/b] the historical "Cloak Disabled" idea is [b]not[/b] currently supported as a recovered Battlezone 1.5 host contract. The 1.5 executable/symbol/string audits did not establish a bCloak-style rule or shell option. If OpenShim eventually adds a lobby cloak rule, it should be documented as a [b]new OpenShim multiplayer feature[/b], not a legacy-option restoration.

[h3]Editor / Campaign / UI Bugs[/h3]

[list]
[*] [b]Editor Shift-F10 object-placement regression[/b] - pre-Redux behavior allowed placement without manually pausing. Reproduce and compare the placement gate against legacy behavior.
[*] [b]Campaign mission-end screens[/b] - stock/custom paths share result IDs 0x13/0x14; custom divergence is later metadata/progression and generic screen-0x25 reconstruction. Capture the failing custom-final transition before patching.
[*] [b]Custom-campaign end screen focus/minimize bug[/b] - Redux explicitly calls SW_MINIMIZE on fullscreen WM_ACTIVATEAPP deactivation. The prepared trace should identify the activation-loss producer before minimize policy is changed.
[*] [b]Legacy heightmap smoothing compatibility[/b] - Redux deliberately added legacy HGT smoothing/upscaling behavior, and 2.2.301 itself removed smoothing from Great Pyramid to restore its authored stairs. The task is no longer merely to ask whether the default changed; it is to define a safe legacy-compatible HGT/HG2 policy and validate it against known stock controls such as Great Pyramid.
[/list]

[h3]Rendering / Animation Bugs[/h3]

[list]
[*] [b]Terrain type-0/orientation deformation[/b] - the terrain pipeline is now deeply mapped, including the 9409-vertex / 38400-index cluster layout and logical tile/orientation chain, but a systematic transition/rotation validation matrix is still needed before calling the visual issue solved.
[*] [b]Skeletal animation rate handling[/b] - person/skeletal animation can ignore VDF/ODF speed values such as animRate and instead run at hard-coded rates.
[*] [b]Skeletal animation looping[/b] - some skeletal animations authored to loop play only once. The native animation-state policy needs to be identified and exposed or corrected.
[/list]

[h3]Resource Loading / Mod Isolation[/h3]

[list]
[*] [b]Unrelated mod resources loading when a menu/category opens[/b] - the Ogre material-name conflict guard prevents many duplicate-material hard crashes, but Redux can still initialize resources from unrelated subscribed mods before selected content is actually launched.
[*] Long-term goal: metadata-first enumeration plus selected-mod/dependency resource loading so one mod cannot accidentally poison another mod's resource namespace.
[/list]

[h2]Implemented - Qualification Pending[/h2]

These items are no longer speculative backlog entries, but each still has a meaningful acceptance gate.

[list]
[*] [b]Battlezone 1.5 satellite fog-of-war restoration[/b] - the 1.5 satellite submission rule was reconstructed as an illumination gate and restored for single-player. Lifecycle cases such as pre-hidden entities, objects created/destroyed while satellite is open, and mission teardown were hardened and runtime-tested. The feature deliberately stands down in network games for parity because otherwise an OpenShim client would see fewer enemies than a stock peer.
[*] [b]Custom-campaign/map BMP thumbnail crash guard[/b] - the root cause is proven: bundled FreeImage rejects unsupported BMP variants such as BITMAPV5HEADER, Ogre converts that to an uncaught C++ exception, and the process terminates. OpenShim catches only the expected decode exception and substitutes the stock UI material. Remaining work is repeat-selection/consumer qualification, not root-cause discovery.
[*] [b]TRN tile-blending control[/b] - [OpenShim] TerrainTileBlend=0..1 remaps Redux's proven seam-alpha mask. Mapping/resolver tests pass; live visual acceptance and equivalent Steam lifecycle coverage remain.
[*] [b]Finite craft-bounds restoration / frustum culling[/b] - Redux's cockpit path can write an infinite bound onto shared world craft meshes, defeating Ogre culling and PSSM cascade assignment. OpenShim can restore a finite containment-safe bound and has measured large submission reductions. Keep final visual/camera/save-load qualification visible.
[*] [b]DX11 Enhanced dynamic-light ranking[/b] - the Enhanced shader already supports 24 lights and experimental contribution-ranked candidate selection exists; final human visual/performance acceptance remains.
[*] [b]Enhanced lighting art-direction corrections[/b] - double-encoded fog and the neutral terrain IBL floor are corrected and automated shader/runtime checks pass; locked-camera art-direction recapture remains the release gate.
[*] [b]PSSM shadow-far-distance override[/b] - the 128m receiver cutoff root cause is mapped and a narrow override experiment exists. Final policy still needs visual/quality qualification rather than blindly changing a global distance.
[*] [b]Legacy scrap/pilot HUD reconstruction[/b] - BZ 1.5 layout, black backplates, colors, and command-menu-relative placement have been reconstructed in UI design space. Continue normal gameplay/resolution acceptance before treating every layout edge case as permanently closed.
[/list]

[h2]Disproven / Reclassified Historical Reports[/h2]

These entries are kept here so old tracker discussions do not silently re-enter the bug backlog later.

[list]
[*] [b]Howitzer Artillery weaponMask[/b] - [b]not a Redux regression[/b]. BZ 1.5 also selects the first fitted weapon and does not read weaponMask in ArtilleryProcess::DoAttack. OpenShim's weaponMask-aware selector is an optional single-player enhancement, default off.
[*] [b]Minelayer Lay Mines weaponMask[/b] - [b]not a Redux regression[/b]. BZ 1.5 hard-codes hardpoint 0 and selected mask 1 in LayMinesTask::DoArrived. OpenShim's alternate selection is the same optional enhancement class as the artillery change.
[*] [b]WeaponMine hop-out / perceivedTeam ownership theory[/b] - [b]disproven[/b]. WeaponMine hostility resolves the candidate's actual team in both builds; AbandonPilot's perceivedTeam write cannot cause the proposed allied-mine hostility. The one-time hop-out attack growl is a separate CockpitRadar stale enemyShot alert and has its own narrow suppression option.
[*] [b]Reveal-on-engagement as a compatibility repair[/b] - [b]reclassified as an enhancement[/b]. Stock 1.5 reveals an attacker when hostile damage lands; it does not generally reveal the process owner just because AI begins engaging. The old OpenShim attack-reveal hooks are quarantined and must not be described as a 1.5 restoration.
[*] [b]Cloak Disabled as a legacy host option[/b] - [b]not established[/b]. No 1.5 host-rule contract has been reconstructed. Treat any future lobby cloak control as a new OpenShim rule unless new evidence proves otherwise.
[*] [b]Enable Large Address Aware as a memory fix[/b] - [b]not applicable[/b]. Windows Redux 2.2.301 is already LAA; focus x86 memory work on retention/fragmentation instead.
[/list]

[h2]Long-Term Goal[/h2]

The long-term goal is still not to throw away Battlezone 98 Redux and casually replace it with a new engine.

The near- and medium-term goal is to make the existing game:

[list]
[*] More stable
[*] Easier to mod
[*] Better behaved on modern systems
[*] More consistent between Steam and GOG
[*] Less dependent on external services remaining online forever
[*] More memory-resilient within the limits of the existing 32-bit Windows executable
[*] Capable of supporting more ambitious community content than the stock scripting/API surface allows
[/list]

OpenShim handles the things that require native engine access.

Extra Utilities exposes more of that functionality cleanly to Lua.

Campaign Reimagined provides a real-world environment where those systems can actually be tested rather than existing only as experimental hooks.

The matchmaking/server work is intended to keep multiplayer usable long-term.

And the new symbol-rich macOS x64 peer build gives us a serious research path for understanding what a true Windows x64 reconstruction would require if the community eventually decides that the 32-bit executable itself has become the limiting factor.

There is still a lot to reverse engineer, validate, and clean up, but the project has reached the point where some ideas that would have been unrealistic a year ago are now genuinely feasible.
