[h1]Roadmap[/h1]

This is the authoritative roadmap and backlog for the Battlezone 98 Redux community patch / OpenShim / Extra Utilities work.

[b]Last major audit: 2026-09-05.[/b]

This file now supersedes the old ExtraUtilities [code]FeaturesToLookInto.txt[/code] tracker as the source of truth. Older tracker items have either been folded in here, marked completed/reclassified, or retained below as lower-priority research ideas.

This is [b]not a promise that features will arrive in this exact order[/b]. A lot of this work depends on reverse engineering, testing, and whether a feature can be implemented safely without introducing worse problems than it solves.

The general priority remains:

[b]Fix crashes and broken stock behavior first, then improve compatibility and multiplayer longevity, then expand the modding API and visual features.[/b]

[h2]Status Legend[/h2]

[list]
[*] [b]Active / Open[/b] - the defect or feature is genuinely unresolved.
[*] [b]Implemented - Qualification Pending[/b] - code exists, but live, multiplayer, visual, or lifecycle acceptance still has a meaningful open gate.
[*] [b]Completed / Restored[/b] - sufficiently understood, implemented, and qualified to leave the active backlog.
[*] [b]Inherited / Legacy Defect[/b] - confirmed to exist in stock 1.5 or an earlier engine, but still considered erroneous or undesirable.
[*] [b]Disproven / Reclassified[/b] - the old root cause was wrong, the report is not reproducible, or the work belongs to another track.
[/list]

[h2]High Priority[/h2]

[h3]GOG Workshop Compatibility[/h3]

Steam users automatically download Workshop content required by multiplayer games. GOG users do not.

The goal is an [b]optional GOG Workshop bridge[/b] that can identify a required Workshop item, offer to download it through a small external helper, validate/stage it into a GOG-visible mod location, refresh content, and retry joining.

Network/download work should remain outside the game process and explicitly opt-in.

[h3]Mod Dependency Support[/h3]

Battlezone does not understand Workshop dependency relationships even when Steam has downloaded the required items.

OpenShim should eventually understand a real dependency graph so it can:

[list]
[*] Detect missing dependencies
[*] Detect installed-but-unavailable dependencies
[*] Recursively resolve dependency chains
[*] Present useful errors instead of mysterious missing assets
[*] Integrate dependency staging with the GOG Workshop bridge
[*] Support optional minimum OpenShim / EXU versions and resource/load requirements later
[/list]

[h3]32-bit Mission Resource / Address-Space Lifecycle[/h3]

Windows Redux 2.2.301 is already Large Address Aware. The practical x86 problem is resource retention and/or virtual-address fragmentation across large custom campaigns.

Plan:

[list]
[*] Add committed/private/working-set and virtual-address telemetry
[*] Track total free VA and the largest contiguous free region
[*] Count Ogre textures, meshes, skeletons, materials, and Modable resources around mission transitions
[*] Use a deterministic multi-mission heavy-asset fixture to prove or disprove cumulative retention
[*] Only after retention is proven, identify the safest teardown/unload window
[/list]

[h3]Windows x64 Reconstruction Research[/h3]

The shipped macOS 2.2.301 executable is a true x86-64 peer build and preserves C++ names, RTTI, vtables, function starts, unwind metadata, translation-unit names, and direct 64-bit object layouts.

DistributedObject and GameObject have already been reconstructed against the Windows reader. The current evidence says the game architecture itself is effectively 64-bit clean: network IDs are fixed-width, the wire format agrees across Mac x64 and Windows x86, registries are keyed by IDs rather than addresses, and Lua handles are 32-bit opaque identifiers.

The obstacle to a native Windows x64 build is not pointer width; it is reconstructing a very large source-less codebase and replacing Windows-specific middleware/ABI assumptions.

This remains research, not a promise to replace Redux.

[h2]Implemented - Qualification Pending[/h2]

These items have working code but still have a meaningful acceptance gate.

[list]
[*] [b]Live lobby nickname propagation[/b] - reworked on 2026-09-05 after live qualification failed. The connection-time nickname buffer is read at exactly one point, while the Authorization body is built, so writing it mid-session cannot by itself change what peers see - which is why a rename only ever appeared after a restart. The [code]SetPlayerData("name", value)[/code] path is no longer used: no observer saw a rename from it. Instead, with [code][Network] ReauthOnNicknameChange = 1[/code] (default off) a rename made in a lounge or lobby queues a second Authorization on the existing connection, and the same stable Steam/GOG identity re-appears with the new name without restarting. In a match, or with no lobby, the rename is saved for the next connection and says so - it no longer claims to have applied live when it has not. Remaining gate: a real second client confirming the rename is visible, then re-auth stability across Steam, GOG and Galaxy. The 2026-09-04 run never reached a positive GOG control because Galaxy's communication service failed.
[*] [b]Stock Factions multiplayer pool[/b] - [code][Network] StockFactionsOnly[/code], default off, restores the restrictive 1.5 starting-vehicle pool by pruning unwanted factions after the list is built. Remaining gate: two-client qualification with the rule on and off.
[*] [b]TRN tile-blending control[/b] - [code][OpenShim] TerrainTileBlend=0..1[/code] remaps Redux's proven seam-alpha mask. Mapping/resolver tests pass; live visual acceptance and Steam lifecycle coverage remain.
[*] [b]Finite craft-bounds restoration / frustum culling[/b] - restores a finite containment-safe bound after Redux cockpit code can write an infinite world-craft bound. Submission reductions are measured; final visual/camera/save-load qualification remains.
[*] [b]DX11 Enhanced dynamic-light ranking[/b] - the Enhanced shader supports 24 lights and contribution-ranked candidate selection exists experimentally; final human visual/performance acceptance remains.
[*] [b]Enhanced lighting art-direction corrections[/b] - double-encoded fog and the neutral terrain IBL floor are corrected and automated checks pass; locked-camera art-direction recapture remains the release gate.
[*] [b]PSSM shadow-far-distance override[/b] - the 128m receiver cutoff root cause is mapped and a narrow override exists. Final policy still needs visual/quality qualification.
[*] [b]Legacy scrap/pilot HUD reconstruction[/b] - BZ 1.5 layout, black backplates, colors, and command-menu-relative placement are reconstructed. Continue normal gameplay/resolution acceptance.
[/list]

[h3]Reactive HUD / Hit Feedback[/h3]

[h3]Legacy Battlezone 1.4 AI Behavior[/h3]

UnitTask and pathfinding changed substantially between 1.4 and 1.5. The intended direction is an opt-in per-ODF [code]aiName[/code]/profile for selected legacy behavior, never a silent replacement of stock Redux AI. Correctness, save/load, and multiplayer determinism remain open.

The Red Odyssey 1.3 comparison establishes Cloak and Portal plus a widened nation enum as its major engine additions; TRO and 1.5 should not be treated as interchangeable reference points.

[h3]Multiplayer Bugs[/h3]

[list]
[*] [b]Packet-loss / traffic-storm recovery[/b]
[*] [b]Armory / Daywrecker duplicate detonation[/b] - no owner-only source boundary has been established. Both detonation bodies share a consumed byte, and the two explosion paths cannot be assumed cosmetic, so a guess at an authority guard risks removing real damage. Blocked on a two-peer capture rather than on more static analysis.
[*] [b]Daywrecker terrain-spire corruption[/b] - the crater routine is non-idempotent if it runs twice over the same buffer, but one call on the host plus one on the client is not two calls on either buffer, so that alone does not explain the reported spires. Same two-peer gate as above.
[*] [b]Splinter multiplayer payload duplication[/b] - still open, but the long-assumed cause is now contradicted. The deployed producer zeroes its payload's send flag immediately after building it, and the send path only processes a nonzero flag, so the payload is not transmitted and the other peer is not receiving a duplicate copy of it. Whatever is being observed, it is not this chain; an owner-build/send/remote-receive gate would not fix it.
[*] [b]Splinter deployed collision response[/b]
[*] [b]Password-lobby friend invites[/b] - invite path omits the password.

[h2]Completed / Restored[/h2]

The following have moved out of the speculative backlog into working/qualified code or a sufficiently proven compatibility result:

[list]
[*] [b]Linux/Proton crash-report and runtime-log hardening[/b] - OpenShim now starts a fresh crash report for each process and labels caught first-chance exceptions separately from fatal crashes, so old or recovered faults are no longer presented as the cause of a later session. Expensive Ogre vehicle/chunk research probes are opt-in again, and multiplayer routing/reorder diagnostics are sampled or emitted once per reason instead of writing hundreds of thousands of packet-path lines during a match.
[*] [b]Multiplayer nickname crash fix[/b] - typing [code]/nickname[/code] during a match could terminate the game. The lobby route-display widgets are destroyed when the match starts, but the refresh that runs after every accepted rename only checked that its cached pointer was non-null before handing it to the engine. It now requires the widget to still be a live child of its owning screen, and clears the stale pointers when it is not. This ran outside the live-nickname setting, so turning that off did not avoid it.
[*] [b]Engine-level career statistics[/b] - kills, deaths, and missions played are tracked across single player and multiplayer without mission script support, controlled by [code][Career] StatsTracking[/code], stored locally, and resettable from the Settings page.
[*] [b]Battlezone 1.5 satellite fog-of-war restoration[/b] - the legacy illumination rule works in single-player, including lifecycle handling; it deliberately stands down in network games for parity.
[*] [b]Native Redux Raw Input support[/b] - Redux's real WM_INPUT path is exposed through OpenShim with an explicit INI/UI control and absolute-mode device handling.
[*] [b]Player/AI headlight controls and falloff/range repair[/b] - OpenShim exposes player and AI headlights, named/custom RGB color/intensity, focused/wide beam shaping, and repaired spotlight falloff/attenuation-range behavior instead of the old hard terminator.
[*] [b]Pilot flashlight[/b] - the player's pilot now carries its own spotlight on foot, off by default under [code][SinglePlayer] PilotFlashlight[/code] with color, beam shape, source bone, offset, and pitch controls, plus Settings-page rows for the first three. Stock only builds a light for a mesh whose skeleton has an [code]hlgt[/code] bone and no pilot skeleton has one, so this is a new light built the same way the engine builds a vehicle headlight and attached to the pilot's own scene node. Live measurement showed the first-person gun bone sits at the skeleton origin and carries no aim at all; the aim is on the node, which is why the beam follows where you look. Single player only.
[*] [b]Per-tick feature drivers no longer gated behind chunk rendering[/b] - both of the shim's per-tick drivers were filtered out whenever [code][General] ChunkMeshes[/code] was 0, which is the shipped default. On a default install that silently disabled the stock headlight controls, the radar layout fix, the multiplayer-gate reconcile tick, the multiplayer flag render fallback, the satellite visibility sync, and several deferred hook installs. Only the genuine chunk-render experiment stays behind that flag now.
[*] [b]First-person gun bone aim mapping[/b] - reclassified. A gun-mounted pilot light cannot be driven from the first-person weapon bone: it is static at the skeleton origin and the aim lives in the pilot's scene node. Recorded so the idea is not re-attempted from the old assumption.
[*] [b]Defensive turret pitch control[/b] - [code]TurretAimPitch[/code] and [code]TurretAimPitchMultiplier[/code] already provide the global OpenShim pitch-authority control. Per-ODF/generalized aim limits remain a separate possible extension above.

[h2]Long-Term Goal[/h2]

The goal is not to casually throw away Battlezone 98 Redux and replace it with a new engine.

The near- and medium-term goal is to make the existing game:

[list]
[*] More stable
[*] Easier to mod
[*] Better behaved on modern systems
[*] More consistent between Steam and GOG
[*] Less dependent on external services remaining online forever
[*] More memory-resilient within the limits of the 32-bit Windows executable
[*] Capable of supporting more ambitious community content than the stock scripting/API surface allows
[/list]

OpenShim handles the pieces that require native engine access.

Extra Utilities exposes more of that functionality cleanly to Lua.

Campaign Reimagined provides a real-world environment where these systems can be exercised rather than existing only as isolated hooks.

The matchmaking/server work is intended to preserve multiplayer long-term.

The symbol-rich macOS x64 peer build gives the project a serious research path for understanding what a true Windows x64 reconstruction would require if the 32-bit executable eventually becomes the limiting factor.
